# 目录布局（layout v1）

治理阶段 B 与新建模式的操作细则。

核心原则：**一类东西只有一个名字、一个位置**。顶层统一按组件分目录，单组件工程也一样；骨架像 CubeMX 那样固定，人只往固定位置填内容。

## 1. 顶层骨架

```
<工程>/
├── README.md  VERSION  CLAUDE.md  .gitignore     ← 根目录只有说明与配置
├── firmware/                固件，一块板一个子目录
│   ├── <板目录>/            CubeMX/Keil 工程整体，目录名 = .ioc 名
│   └── build_fw.bat         （可选）全部固件的命令行构建
├── host/                    上位机（多个时 host/<名>/）
├── server/  web/  app/      后端 / 前端 / 移动与大屏终端（按需）
├── deploy/                  部署（按需）
├── contracts/               机器可读接口契约（按需）
├── tools/                   开发辅助（按需）
├── tests/                   测试（按需，多组件时 tests/<组件>/）
├── docs/                    文档十类（文档整理.md §3）
└── release/                 当前交付物（gitignore）
```

只建有内容的目录，不放 `.gitkeep`。同类组件只有一个时直接用组件目录（`host/`），多个时分子目录（`host/<名>/`）；固件例外，总是 `firmware/<板目录>/`。

## 2. 全局词表

单一来源是 `scripts/scan.py` 的 `LAYOUT_V1`，本表由 `tests/test_scan.py` 校验两者一致。新增或删除词时两处同改。

| 词 | 含义 | 放什么 | 不放什么 |
|---|---|---|---|
| `firmware/` | 运行在 MCU 上的程序 | `firmware/<板目录>/`；同层可放固件共用的 `build_fw.bat` | 上位机、测试 |
| `host/` | 用户在 PC 上运行的程序（GUI、CLI、桌面应用） | 源码、依赖清单、自身的 `run_*.bat`/`pack_exe.bat`、README | 只给开发者用的辅助（→ `tools/`） |
| `server/` | 后端服务 | 服务源码、配置模板、组件内运行时数据目录（gitignore） | 部署编排（→ `deploy/`） |
| `web/` | 浏览器前端 | SPA/页面工程整体 | — |
| `app/` | 移动端、TV 大屏等终端 App | 多个时 `app/<名>/` | — |
| `deploy/` | 部署 | compose、Dockerfile、nginx、安装包工程（`deploy/installer/`）、现场启停脚本 | 开发期启动脚本（→ 组件内） |
| `contracts/` | 机器可读接口契约 | OpenAPI、JSON Schema、proto，被代码生成或测试引用 | 纯文字接口说明（→ `docs/接口/`） |
| `tools/` | 开发辅助，不交付 | 协议帧校验、Keil 清理、代码生成、批量构建 | 组件自己的启动/打包脚本 |
| `tests/` | 测试 | 测试代码、fake/stub、fixtures、HIL 脚本 | 运行结果与日志（→ scratchpad）、台架记录（结论 → `docs/问题记录/`） |
| `docs/` | 文档 | 十类：协议、接口、需求、参考资料、方案、问题记录、记录、手册、报告、模板（[文档整理.md](文档整理.md) §3） | — |
| `release/` | 当前交付物 | 见 [版本与发布.md](版本与发布.md) §8 | — |

**生态容器词**（仅工作区型工程，即根目录有 `pnpm-workspace.yaml`/`turbo.json`/`nx.json`/`lerna.json`、`package.json` 带 `workspaces`，或 `*.sln`）：`apps/`、`packages/`（Node）；`src/`（.NET，测试沿用根 `tests/`）。容器内部不动。

**组件内部词**：固件 `User/App`（业务与协议）、`User/BSP`（板级外设封装）、`User/ThirdParty`（非 CubeMX 管理的第三方库）、`Drivers/`（标准库固件的厂商库与 CMSIS）；非固件组件的第三方依赖用 `ThirdParty/`；运行时数据 `data/`、`uploads/`、`models/`、`logs/` 放在所属组件内并加入 gitignore。

**词表扩展**：新用途先尝试归入已有词；归不进的，用 AskUserQuestion 问用户，写清「含义 / 放什么 / 不放什么」且与已有词无重叠。批准后同时改本表和 `LAYOUT_V1`，所有工程共用。不设工程级私有词。

## 3. 根目录白名单

| 允许 | 内容 |
|---|---|
| 说明与配置 | `README.md`、`VERSION`、`CLAUDE.md`、`AGENTS.md`、`.gitignore`、`.gitattributes`、`.gitmodules`、`.editorconfig`、`LICENSE`、`CHANGELOG` |
| 工作区型生态文件 | `package.json`、各类 lock 文件、`pnpm-workspace.yaml`、`turbo.json`、`tsconfig*.json`、eslint/prettier/commitlint/lint-staged 配置、`*.sln`、`Directory.Build.props`、`Directory.Packages.props`、`global.json`、`NuGet.config`、`requirements*.txt` |
| 工具配置目录 | `.github/`、`.gitea/`、`.vscode/`、`.claude/`、`.idea/`、`.husky/`、`.kiro/`、`.cursor/` 等 |
| 可再生环境目录 | `node_modules/`、`.venv/`、`venv/`、`__pycache__/` 等（gitignore） |

不允许：任何 `.bat/.cmd/.ps1/.sh/.py/.vbs` 脚本；README/CLAUDE/AGENTS 以外的文档；图片；根级 `dist/`、`build/`；非工作区工程根目录的应用构建配置（`package.json`、`vite.config.*` 等随组件走）；compose/Dockerfile（→ `deploy/`）。

## 4. 组件内规则

### 4.1 固件 · CubeMX

- `firmware/<ioc名>/` 整体搬入（uvprojx 全部是相对 `MDK-ARM/` 的路径，整体搬迁不用改构建配置）
- `Core/`、`Drivers/`、`Middlewares/`、`FATFS/`、`USB_HOST/`、`USB_DEVICE/`、`LWIP/`、`MDK-ARM/`、`EWARM/` 等生成目录不动；板目录内只允许新增 `README.md` 和 `User/`，不放脚本（`keilkill.bat` → `tools/clean_keil.bat`）
- 自写代码进 `User/{App,BSP,ThirdParty}`，代码少时可只有 `App/`。判定 `Core/` 下的自写文件：既无 `USER CODE BEGIN` 标记、也无 STMicroelectronics 版权头
- 搬出 `Core/` 时，uvprojx 新建 `Application/User/App` 等分组，**插在原文件所在位置**（链接顺序不变，hex 才能逐字节一致），`IncludePath` 加 `../User/App`。实测重新生成后这些分组和路径都会保留
- 目录名 = ioc 名是命名约定；**硬约束是 `ProjectName` = uvprojx 文件名**，否则重新生成会另起一个新 uvprojx 并丢失用户分组
- 多 MCU：`firmware/<板1>/`、`firmware/<板2>/`；板间共享代码出现时走词表扩展（候选 `firmware/Common/`）

### 4.2 固件 · 标准库（非 CubeMX）

- `firmware/<uvprojx 工程名>/{Drivers/, User/{App,BSP,ThirdParty}, MDK-ARM/}`
- `Library/`、`Libraries/`、`FWLIB/` 等厂商库目录 → `Drivers/`；`lvgl/` 等第三方 → `User/ThirdParty/`
- 迁移 = 目录移动 + uvprojx 内 `FilePath`/`IncludePath` 批量替换（如 `..\Library\` → `..\Drivers\`），替换时保持文件和分组顺序

### 4.3 上位机 · Python

- `host/`：`*.py`（约 10 个以内平铺，多了改包目录）、`requirements.txt`、`run_<名>.bat`、`pack_exe.bat`、`README.md`
- `pack_exe.bat` 是 PyInstaller 打包命令的单一来源，输出到 `host\dist`、`host\build`（同盘符）；spec 不入库；发布流程从 `host/dist/` 复制到 `release/` 并按版本命名
- `tools/` 里的 GUI 程序 scan 只标「复核」：交付给用户的才迁 `host/`，开发者自用的留在 `tools/`

### 4.4 前后端

- 单应用型：Tauri/Electron 桌面 → `host/`，SPA → `web/`，Express/Flask/ASP.NET → `server/`；内部生态骨架原样（Tauri 的 `src-tauri/` 与 `package.json` 同在组件目录）
- 工作区型：根目录即工作区，内部不动；只管 `deploy/ tools/ docs/ release/` 和根目录白名单
- 运行时数据目录跟所属组件走；现场在用的（最近 24 小时有写入、名字含 current/live）先问

### 4.5 脚本

- ASCII「动词_对象」：`run_gui.bat`、`pack_exe.bat`、`build_fw.bat`、`flash_fw.bat`、`clean_keil.bat`、`start_server.bat`、`stop_server.bat`
- `.bat` 正文纯 ASCII，中文提示放 Python 层（含中文的批处理会被 cmd 按字节拆碎）
- 脚本里用 `%~dp0` 定位自身，不依赖当前目录；模板见 `templates/scripts/`

## 5. README 目录表

- 根 README 必须有 `## 目录结构`，下接 `| 路径 | 内容 |` 表，第一列用反引号包路径
- scan 双向校验：每个有跟踪内容的顶层目录、每个组件子目录（`firmware/<板>` 等）都要有一行，或有一行的路径在它下面；表里列了但已不存在的路径也报。第一列含「分支」的行、绝对路径行、`release/`（gitignore，新建或刚 clone 时本来就不存在）不做存在性校验
- 组件 README 写构建/运行/烧录/打包方法；CubeMX 板目录的 README 放在板目录内

## 6. 阶段 B 执行细则

前置：阶段 A 已完成、工作区干净；提醒用户关闭 Keil、VS Code 等占用工程文件的程序。

1. `scan.py <工程> --json`，读 `phase_b`：`components`（类型、当前位置、期望位置、`review`）、`moves`、`root_violations`、`unknown_dirs`、`readme`、`ioc_issues`、`firmware_internal`、`docs`
2. 逐项核实定稿迁移表。scan 只给证据：组件归属按构建配置的引用关系和 import 关系推断，`review` 项、根目录型组件逐项认领的结果都要人工看一遍
3. **一次确认**（一条消息）：before/after 目录树；构建配置改动清单（uvprojx 哪些 `FilePath`/`IncludePath`/分组、`.gitignore`、脚本内路径）；文档链接替换数；争议项（ioc 改名、某文件归 App 还是 BSP、tools/ 里的 GUI 是否交付等）用 AskUserQuestion 逐个问；工程外可能引用的入口（桌面快捷方式、计划任务、部署机上的启停脚本）
4. **基线**：搬迁前构建一次，记录 hex 的 SHA-256 和测试结果（写 scratchpad）
5. 执行：
   1. 建目标父目录，`git mv` 搬迁。目录 rename 会连同未跟踪的编译产物一起搬走；目标父目录不存在时 `git mv` 会失败
   2. 构建配置最小改动（§4.1、§4.2），保持文件与分组顺序；uvprojx 改了分组，uvoptx 的分组镜像（`GroupNumber`）也同步改。用脚本改时按字节读写、**沿用文件自己的换行符**：即使 `core.autocrlf=true`，工作区文件也可能是 LF（`git archive` 导出的副本却是 CRLF，在副本上调通的替换不一定能匹配真实工作区），每处替换断言只命中一次，不命中就整体放弃写入
   3. 全文替换旧路径：README、CLAUDE.md/AGENTS.md、`docs/`、代码注释、脚本（`git grep -n -I -F "<旧路径>"`，正反斜杠两种写法都查）
   4. 文档归入 `docs/` 十类（`git mv` + 修正链接；命名与各类版本规则见[文档整理.md](文档整理.md) §3；协议文档重命名为 `<协议名>_V<主.次>.<ext>`）
   5. 补齐根 README 目录表和组件 README；VERSION 加 `layout = 1`
6. 验证（§7），全部通过才继续
7. 提交「重构: 目录布局接入 layout v1（<一句话>）」，正文写迁移表摘要和恢复方法 `git revert <提交>`。代码文件只搬不改内容，保证 `git log --follow`、`git blame -M` 能追溯
8. 复扫：`phase_b.issues` 为 0；`git status` 干净

## 7. 验证门槛

| 工具链 | 命令 | 通过标准 |
|---|---|---|
| Keil MDK | `UV4.exe -b <uvprojx> -j0 -o <scratchpad>\build.log`（`UV4.exe` 先取环境变量 `UV4`，没有再找 `%LOCALAPPDATA%\Keil_v5\UV4\`、`C:\Keil_v5\UV4\`；都没有就问用户） | 0 Error；纯搬迁时 hex SHA-256 与基线一致 |
| IAR EWARM | 不做命令行构建 | 只做引用检查，提示用户编译 |
| Python | `python -m py_compile` 全部 + 工程自带 `--selftest`/`--smoke` | 退出码 0 |
| Node | 按锁文件选包管理器跑 `build`/`typecheck` | 退出码 0 |
| .NET | `dotnet build` | 退出码 0 |

- hex 不一致时先停下说明原因：① 链接顺序变了（uvprojx 文件或分组顺序）；② `__FILE__` 字符串（开了 `USE_FULL_ASSERT`）；③ 编译器版本不同
- **不用 CubeMX 重新生成当验证门槛**：重新生成有副作用（GD 器件被写回 STM32、Drivers 换行符变 LF、删除未用驱动），无人值守运行还可能卡在「New STM32Cube firmware version available」模态框。用户明确要求验证"重新生成是否安全"时，先把工程 `git archive` 到 scratchpad，再用 `scripts/run_cubemx.ps1 -Ioc <副本 ioc>` 跑：出现对话框它会结束进程并报出标题（退出码 3），此时交给用户在 GUI 里处理
- 判断 hex 是否新鲜：构建前记下时间，构建后确认 hex 的修改时间晚于它，避免"编译失败、旧 hex 仍在、哈希碰巧一致"的假通过；`firmware/build_fw.bat` 失败时返回非 0
- 上位机：`run_gui.bat` 用 `start pythonw` 异步启动，拿不到退出码，冒烟以 `python <入口>.py --smoke` 为准；`pack_exe.bat` 重建后对新 exe 跑 `--smoke`
- 失败恢复：阶段开始时工作区是干净的，`git reset --hard HEAD` 只丢弃本阶段改动；本阶段新建的未跟踪文件按清单移入回收站（不用 `git clean`）；被 `git mv` 一起搬走的未跟踪编译产物按迁移表搬回

## 8. 改名方案（CubeMX / Keil）

板目录名或工程名看不出含义（scan 的 `ioc_issues`，线索：test、tets、new、copy、demo、old、副本、新建）时，给出改名方案，用户确认后一次改齐：

| 项 | 位置 |
|---|---|
| ioc 文件名 | `<板目录>/<新名>.ioc` |
| `ProjectManager.ProjectName`、`ProjectManager.ProjectFileName` | ioc 内（保留原换行符） |
| uvprojx / uvoptx 文件名 | `MDK-ARM/<新名>.uvprojx`、`.uvoptx` |
| `TargetName`、`OutputName`、`OutputDirectory` | uvprojx 与 uvoptx 内 |
| 板目录名 | `firmware/<新名>/` |
| `.gitignore` 中的输出路径、README/CLAUDE.md 中的引用 | 全文替换 |

只改 ioc 不改 uvprojx 会让 CubeMX 另起一个全新 uvprojx；全部改齐后重新生成会原地更新，改名本身不改变 hex（均经实测）。用 Python 改文件时按字节读写，不要用文本模式转换换行符。

## 9. 已知词表外目录的建议归属

| 现有 | 归属 |
|---|---|
| `scripts/`（与 `tools/` 并存时尤其要合并） | 组件自己的入口归组件，其余进 `tools/` |
| `installer/` | `deploy/installer/` |
| `sdk/`、`vendor/` | 构建引用的 → `<组件>/ThirdParty/`；仅供参考的 → 参考库 |
| `参考资料/`、`开发资料/`、`参考文件/`、`参考文档/` | 器件规格书 → `docs/参考资料/`；大件厂家资料包 → 参考库 |
| `data/`、`uploads/`、`models/`、`logs/` | 所属组件内（如 `server/data/`），gitignore |
| `backend/`、`frontend/`、`mobileapp/` 等 | `server/`、`web/`、`app/<名>/` |
| 根目录 `dist/`、`build/` | 构建输出放组件内；交付物进 `release/` |
