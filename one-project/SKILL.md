# one-project

> **不变量**：一个工程目录 = 一个 git 仓库 = 一份工作区 = 当前分支的一套代码和产物。版本差异只存在于 git 历史（分支 / tag）。唯一例外：规范本体文档（通信协议、接口契约、需求规格、器件规格书）可多版本并存。
>
> **git 即档案**：已跟踪的过程文件直接删（历史可取回）；未跟踪的文本类先提交再删；二进制 / 大件 / 可再生目录进回收站；交付物进发布库。skill 本身**不写任何状态文件**。
>
> **文档型工程例外**：VERSION 写 `type = docs` 的文档/素材型工程不用 git，移出的文件一律进回收站，靠 scratchpad 里的留底清单恢复（[文档整理.md](references/文档整理.md) §1）。

判定细则见 [references/判定规则.md](references/判定规则.md)，目录模板与搬迁细则见 [references/目录布局.md](references/目录布局.md)，文档分类与文档型工程见 [references/文档整理.md](references/文档整理.md)，版本/分支/提交/发布见 [references/版本与发布.md](references/版本与发布.md)。新建工程与治理用的模板文件在 `templates/`。

**本机配置**：下文的尖括号占位符按本机实际值替换。

| 占位符 | 含义 | 来源 |
|---|---|---|
| `<skill>` | 本 skill 的目录 | 加载 skill 时给出的基目录 |
| `<工作区根>` | 放工程的目录，直接子目录各是一个工程；可以有多个 | 全局 `~/.claude/CLAUDE.md`「工程卫生（one-project）」一节的「本机路径」 |
| `<发布库>` | 工程外存放正式交付物的目录，按型号分子目录 | 同上 |
| `<参考库>` | 工程外存放参考工程和嵌套仓库的目录 | 同上 |

全局 CLAUDE.md 没有这一节或缺「本机路径」时，先走初始化模式（§9），不要猜路径。运行环境是 Windows，命令示例是 PowerShell 写法；会话里没有 PowerShell 工具时，把片段存成 scratchpad 里的 `.ps1`（UTF-8 with BOM），用 `powershell -NoProfile -ExecutionPolicy Bypass -File <文件>` 运行。`python` 不可用时改用初始化时记下的命令（如 `py -3`）。

`references/存量迁移.md` 是本机的存量待办清单，不随包分发：首次总览后按 `templates/存量迁移.md.tmpl` 建立，完成一项划一项。

## 0. 先定模式

| 用户意图 | 模式 | 会不会改东西 |
|---|---|---|
| 首次使用、初始化 / 配置 one-project，或全局 CLAUDE.md 缺「工程卫生」一节 | **初始化**（§9） | 是，只写全局 CLAUDE.md，确认后 |
| 工程总览、扫一下所有工程 | **总览** | 否 |
| 整理 / 清理 / 体检当前工程、接入版本规范 | **治理**（A 清理 → B 目录布局 → C 版本规范） | 是，分类确认后 |
| 整理目录、目录规范化、规范目录结构 | **治理 · 只跑阶段 B** | 是，迁移表确认后 |
| 整理文档、整理资料、整理文档目录、整理素材；或目标是没有构建配置的文档/素材目录 | **文档整理** | 是，一次确认后 |
| 新建工程、创建工程、工程模板、脚手架 | **新建** | 是，确认组件组合后 |
| 工作区内 git 工程、声明 `type = docs` 的文档型工程，任务即将结束 | **轻检** | 否 |
| 发布版本、打版本、出固件 | **发布** | 是 |
| 只是问问、"先分析别动" | 只跑扫描，出报告 | 否 |

扫描器（只读、无状态，中文路径用 `-X utf8`）：

```powershell
python -X utf8 "<skill>\scripts\scan.py" "<工程路径>"            # 治理前体检
python -X utf8 "<skill>\scripts\scan.py" "<工程路径>" --json     # 需要逐项处理时（phase_a 清理 / phase_b 布局 / phase_c 规范）
python -X utf8 "<skill>\scripts\scan.py" "<工程路径>" --quick    # 轻检
python -X utf8 "<skill>\scripts\scan.py" "<目录>" --docs        # 未声明的文档/素材型目录（声明 type = docs 后自动）
python -X utf8 "<skill>\scripts\scan.py" --workspace "<工作区根 1>" "<工作区根 2>"   # 总览
```

退出码 0 = 无待处理项，1 = 有，2 = 扫描出错。扫描器只给**事实和线索**；"是不是过程文件、哪份是最终版、是不是副本"由你结合内容判断。

## 1. 总览模式

1. 跑 `--workspace`，把报告（各工程一行 + 工作区级杂物 + 跨工程疑似副本 + 跨工程同版本规范文档）给用户。
2. 按清理体积和规范项给出建议的治理顺序。本机已有 `references/存量迁移.md` 就对照它；没有就按 `templates/存量迁移.md.tmpl` 新建，把待办记进去。
3. 跨工程疑似副本只列证据，由用户逐组确认。不改工程里的任何东西。

## 2. 治理模式（单工程）

### 2.1 前置检查（任一不满足即停下问）

- **非 git 工程**：提议按工具链拼 `.gitignore`（`templates/gitignore/` 片段，common 必选），然后 `git init`，提交「构建: 纳入 git 管理，提交现状基线」。用户同意后才继续。
- **工作区有未提交改动**：列出来，问用户是先提交、暂存还是绕开。清理提交绝不夹带用户的改动。
- **当前分支是任务分支**（如 `codex/*`）：先问清这条线的去向（合入 main / 改名为协议线），再清理。
- **存在额外 worktree**：列出，问用户如何合回。

### 2.2 阶段 A：清理（独立提交）

1. 跑 `scan.py <工程> --json`，读取 `phase_a`。
2. 对每个候选做语义核实，规则见 [判定规则.md](references/判定规则.md)。把握为「复核」的条目必须打开看内容；「高」的条目抽查即可。确定每项的**处置方式**：
   - `git rm`：已跟踪的过程文件
   - 先提交再删：未跟踪的文本类过程文件
   - 回收站：未跟踪的二进制、>5 MB、venv/node_modules 类
   - 发布库：真交付过的固件和安装包 → `<发布库>\<型号>\`，保留原名
   - 参考库：嵌套仓库和参考工程 → `<参考库>\<工程名>\<目录名>\`
   - 转分支：整工程副本，按判定规则 §5
   - 保留：核实后发现是正式内容
3. **分类汇总，一次确认**。用一条消息给出：每类的条数、体积、代表样例和处置方式。把**争议项**单独列出，用 AskUserQuestion 逐个问；其余整批批准。任何单项超过所在盘回收站容量（查法见判定规则 §6）时，明确标注"将永久删除"。
4. 按批准执行，顺序如下：
   1. 未跟踪文本 `git add <精确路径>` → 提交「清理: 存档未入库的过程文件」
   2. `git rm -r <精确路径>` → 提交「清理: 移除<类别概述>」，正文写各类计数和恢复方法 `git checkout <本提交>^ -- <路径>`
   3. 回收站、发布库、参考库、副本转分支（这些都不进提交）
5. 复扫：`phase_a` 应只剩用户明确保留的条目；`git status` 干净。

### 2.3 阶段 B：目录布局（独立提交）

按 [目录布局.md](references/目录布局.md) §6 执行，要点：

1. 读 `phase_b`：识别出的组件、建议迁移表、根目录违规、词表外目录、README 目录表缺口、固件命名与内部问题、`docs` 归位（十类，见[文档整理.md](references/文档整理.md) §3；`reclass_hints` 是已按六类整理过的文件疑似该归新四类，顺带重分）。scan 只给证据，组件归属和 `review`（tools/ 里的 GUI）要逐项核实。
2. 词表外目录先按目录布局 §9 归入已有词；归不进的问用户，批准后同时改 `LAYOUT_V1` 和目录布局 §2。
3. **一次确认**：before/after 目录树 + 构建配置改动清单 + 文档链接替换数 + 争议项（AskUserQuestion 逐个问）+ 工程外可能引用的入口。提醒用户先关闭 Keil / IDE。
4. 搬迁前构建一次留基线（hex SHA-256、测试结果写 scratchpad）；`git mv` 搬迁、构建配置最小改动（保持文件与分组顺序）、全文替换旧路径、docs 十类归位、补 README 目录表与组件 README、VERSION 加 `layout = 1`。
5. 验证门槛（目录布局 §7）：必须构建通过，纯搬迁的固件 hex 逐字节一致；任一失败不提交并恢复。
6. 提交「重构: 目录布局接入 layout v1（<一句话>）」，复扫 `phase_b.issues` 应为 0。

### 2.4 阶段 C：接入版本规范（独立提交）

1. 从代码（版本宏、`package.json`、`.csproj`）、协议文档、历史交付物名推断：型号、硬件版次、对外主协议及版本、固件序号。**用 AskUserQuestion 让用户确认**这几项，不要自行拍板。
2. 创建 `VERSION`（格式见版本与发布 §2）；对 `version_files` 做最小修改，让版本号一致。
3. 整理分支：已合并的任务分支直接删除；未合并的列出差异逐个问；变体分支改名为 `protocol/vX.Y-<变体>`；`master` 改为 `main`。远程分支改名属于对外动作，需单独确认。
4. 建 `release/` 并加入 `.gitignore`。交付物带版本号命名，需要改构建配置时，先给出最小改动方案，确认后再做。
5. 提交「构建: 接入 one-project 版本规范（V<版本>）」，然后复扫，`phase_c` 应清零。

已接入版本规范、只差布局的工程，直接跑阶段 B。

## 3. 新建模式（脚手架）

1. 用 AskUserQuestion 问清：工程目录名、型号、组件组合（firmware × N / host / server / web / app / deploy）、各组件技术栈、主协议；版本三段按版本与发布 §2 确认。目标目录已存在且非空就停下问。
2. 按 [目录布局.md](references/目录布局.md) §1 生成骨架，只建有内容的目录：
   - 根目录：`README.md`（`templates/README.md.tmpl`，目录表按实际组件填）、`VERSION`（`templates/VERSION.tmpl`，含 `layout = 1`）、`CLAUDE.md`（`templates/CLAUDE.md.tmpl`）、`.gitignore`（按组件拼 `templates/gitignore/` 片段，common 必选）
   - 组件 README：`templates/component/*.README.md.tmpl`
   - 脚本：`templates/scripts/` 复制后替换 `__ENTRY__`、`__NAME__`、`__EXTRA__` 占位符。`run_gui.bat`、`pack_exe.bat` 放 `host/`，`build_fw.bat` 放 `firmware/`，`clean_keil.bat` 放 `tools/`。复制时保持纯 ASCII + CRLF
   - 模板里的 `{{…}}` 全部替换掉，不留占位符
3. `git init -b main`，`git add` 精确路径，提交「新增: 按 one-project layout v1 初始化工程骨架」。
4. CubeMX 工程：告诉用户在 CubeMX 里 Project Name = 板目录名、Project Location = `<工程>\firmware\`、Toolchain = MDK-ARM；生成后跑一次阶段 B，建 `User/`，并在 uvprojx 加 `User` 分组和 include 路径。
5. 复扫：`phase_b.issues` 为 0，再汇报。

## 4. 文档整理模式

规则全文见 [references/文档整理.md](references/文档整理.md)。代码工程的 `docs/` 走治理阶段 B（§2.3），本模式管文档/素材型工程。

1. **前置**：确认目标目录，提醒关闭占用文件的程序。目录里有构建配置（scan 识别出工具链）的，按代码工程治理，不走本模式。
2. **扫描**：`scan.py <目录> --docs --json`（已声明 `type = docs` 的不用加 `--docs`）。读 `phase_a`（过程文件、同主题多份）和 `phase_b`（根目录散放、词表外目录、带日期目录、docs 十类、assets 三阶段、校验和与清单、子目录 README、重复文件、失效链接、README 三节）。
3. **核实**：重复是否逐字节相同；哪些是 `tools/` 脚本生成的；哪些路径被文档引用。按文档整理 §3–§7 定稿迁移表。
4. **一次确认**：before/after 目录树、搬迁表、回收站清单（条数与体积）、链接改动清单、工程外引用（memory、快捷方式）。争议项用 AskUserQuestion 逐个问，其余整批批准。
5. **留底 → 执行 → 验证**（文档整理 §9）：清单与 SHA-256 写 scratchpad；同盘 `Move-Item` 搬迁、回收站移出、修链接、写 README/VERSION/CLAUDE.md（`templates/*.docs.*`）；核对哈希与条数，复扫布局项、失效链接、规范项都为 0。失败按清单搬回。
6. 同步更新 Claude memory 里指向旧路径的条目。

## 5. 轻检模式

开发任务结束前跑 `--quick`（< 1 秒）。有问题就用一两句话转述给用户，并建议是否需要治理。**不删除、不移动任何东西。** 无问题时不必提。VERSION 声明了 `layout = 1` 的工程，轻检还会拦下布局回退（根目录新增脚本、出现词表外顶层目录、README 目录表漏说明）。声明了 `type = docs` 的文档型工程（不限工作区）按文档整理 §10 拦截。

## 6. 发布模式

按 [版本与发布.md](references/版本与发布.md) §7 执行。要点：

- 前置条件：工作区干净、分支合规、VERSION 自洽、版本号未被 tag 过
- 用当前工程构建（不另建验证工程），交付物写入 `release/`，同时复制进发布库（同名不同内容即停）
- 提交「发布: V<版本>（协议 V<x.y>）」并打同名附注 tag，**自动推送**当前分支和该 tag
- 提醒用户：此版本号已冻结，之后有改动，固件段 +1

## 7. 底线（任何模式都不可违反）

- 不建 worktree、不复制工程目录。只有用户明确要求才建 worktree，用完合回并删除。
- 一次性过程文件（调试脚本、日志、截图、证据、中间报告）写到会话 scratchpad，不在工程里新建 `.artifacts/`、`evidence/`、`tmp/`。
- 不新建任务分支，直接在当前分支提交。分支名只用 ASCII。
- 提交只 `git add` 清单内的精确路径，不用 `git add -A` / `git add .` 去夹带别的改动。
- 永不 force push。永不改写已推送的历史。
- 删除未跟踪文件只走回收站（判定规则 §6），不用 `Remove-Item`。超过回收站容量的，需用户在汇总里明确同意永久删除。
- 发布库和参考库只增不改；目标已存在且内容不同就停下。
- 判定依据是构建配置、引用关系、内容，名字只作线索。正常编译产物（扫描器的"保护路径"）不碰。
- CubeMX 工程不因整理而重新生成代码，也不把重新生成当验证门槛；源码目录迁移、构建配置修改先给方案再动。
- 搬迁前提醒关闭 Keil / IDE；搬迁提交里代码文件只搬不改内容；CubeMX 板目录内只允许新增 `README.md` 和 `User/`。
- 固件改名必须 ioc、ProjectName、uvprojx/uvoptx、Target/Output 一次改齐（目录布局 §8）。
- 文档型工程不 `git init`；搬迁前必须写好留底清单；删除只走回收站。

## 8. 汇报

每次治理、文档整理或发布结束，用简短的中文汇报：

- 做了什么：各类处理的条数和体积，提交哈希，tag（文档型工程没有提交，写留底清单路径）
- 东西去了哪里：发布库、参考库、回收站路径
- 怎么恢复：`git checkout <提交>^ -- <路径>`，或从回收站还原；文档型工程按留底清单搬回
- 复扫结果：剩余项及原因

不另写报告文件。

## 9. 初始化模式（装好后跑一次）

触发：用户说「初始化 / 配置 one-project」；或任何模式开始前发现全局 `~/.claude/CLAUDE.md` 没有「工程卫生（one-project）」一节、这一节缺「本机路径」。日常的预防规则和收尾轻检靠这一节生效，所以它是安装的一部分。

1. **环境检查**（只读）：系统是 Windows；`python --version`（不可用就试 `py -3`，记下能用的那个命令）；`git --version` 不低于 2.28。缺哪样就告诉用户装什么，然后停下。
2. **问清本机路径**（AskUserQuestion，给出建议值）：
   - 工作区根：放工程的目录，它的直接子目录各是一个工程；可以有多个
   - 发布库、参考库：建议 `<工作区根的上级>\releases`、`<工作区根的上级>\references`；现在不存在没关系，第一次用到时再建
   - 轻检范围：默认就是工作区根；多个根有共同上级、用户希望整个上级目录都检时，填上级目录
